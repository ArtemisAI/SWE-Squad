Architecting Full-Autonomy Software Engineering Swarms: Frameworks, Protocols, and Continuous Integration
The contemporary software development lifecycle is increasingly burdened by systemic bottlenecks, characterized primarily by unresolved issues, abandoned bug fixes, and deployments lacking profound testing and evaluation. These deficiencies routinely result in pipeline breakages, fragile codebases, and significant technical debt. To mitigate these risks, the industry is transitioning toward fully autonomous, self-healing agentic swarms. This paradigm shifts artificial intelligence from a passive advisory role into an active, independent engineering workforce. By architecting a "Team of Teams"—a structured swarm of specialized software engineering (SWE) agents—organizations can run a full autonomy architecture parallel to the core automation system. This parallel swarm continuously scans for issues, investigates root causes, proposes solutions, iteratively develops fixes, and rigorously tests them in sandboxed environments before smoothly injecting changes into the core system.
To achieve this, the architecture must leverage the best available open-source orchestration frameworks, relying heavily on standardized communication protocols such as the Agent2Agent (A2A) protocol, the Model Context Protocol (MCP), and the Agent Client Protocol (ACP) via acpx. These connective layers enable disparate coding agents—including Claude Code, Copilot, Goose, and OpenCode—to collaborate seamlessly despite their inherent strengths and weaknesses. Furthermore, the system must adhere to strict efficiency criteria: utilizing free tiers or smaller open-source models for localized, minor tasks, while reserving expensive, high-parameter models like Claude 4.6 Opus strictly for major overall planning and complex architectural governance. The ultimate objective is to establish an ever-improving loop that seamlessly transforms initial probabilistic agentic runs into deterministic, vector-based automations, thereby perpetually reducing token waste and LLM API calls over time.

The open-source ecosystem provides a diverse array of frameworks, each tailored to specific architectural philosophies. Selecting the appropriate framework—or combining them into a composite system—is critical for establishing the boundaries and limitations of each specialized team within the swarm.

The Connectivity Paradigm: A2A, MCP, ACP, and acpx Integration
A swarm of agents cannot function as a cohesive engineering department without standardized communication protocols. The fragmentation of the AI landscape—where tools like Goose, Copilot, and Claude Code operate in silos—must be overcome through a unified connectivity layer. This architecture relies on three critical protocols to ensure that agents possess the required tools, memory, and interoperability.
The Agent2Agent (A2A) Protocol
The Agent2Agent (A2A) protocol, an open standard contributed to the Linux Foundation, serves as the primary communication backbone for the entire SWE swarm. A2A resolves the interoperability challenge, enabling agents built on diverse frameworks running on separate servers to communicate and collaborate effectively as peers, rather than merely as tools.
A2A operates via JSON-RPC 2.0 over HTTP(S) and relies on the concept of "Agent Cards". These cards function as standardized digital identities, containing detailed schema information regarding an agent's specific capabilities, supported interfaces, and connection telemetry. This enables dynamic discovery; an orchestrator can query the network to find an agent equipped with the exact skills required for a sub-task.
Crucially, A2A preserves opacity. Agents negotiate interaction modalities and securely collaborate on long-running tasks without exposing their internal memory, proprietary logic, or tool implementations. This allows the investigation team to pass a diagnostic report to the development team without forcing both teams to share a massive, token-heavy context window. The integration of IBM's Agent Communication Protocol (ACP) into the A2A standard further enhances enterprise compatibility, supporting complex hierarchical workflow orchestration and streaming responses.
The Model Context Protocol (MCP)
While A2A governs peer-to-peer communication between agents, the Model Context Protocol (MCP) dictates how agents interface with external processes, data sources, and the host environment. MCP functions as a universal adapter, standardizing the provision of context to Large Language Models without requiring bespoke API integrations for every new tool.
Within the autonomous SWE architecture, MCP servers are deployed to wrap critical infrastructure. A database investigation agent utilizes an MCP client to securely query a proprietary internal logging database, while a browser automation agent uses a different MCP server to execute Playwright scripts against a DOM. This ensures that all agents have the precise tools needed to execute their boundaries of responsibility while maintaining strict access control.
Integrating Proprietary Coding Agents via ACP and acpx
The swarm architecture demands the integration of highly capable proprietary and open-source coding agents, including Claude Code, Copilot, Goose, and OpenCode. Each of these agents possesses distinct strengths and weaknesses. To coordinate them effectively, the architecture utilizes the Agent Client Protocol (ACP) and the acpx headless CLI client.
The acpx tool translates interactive, human-facing CLI applications into programmatic, session-aware endpoints. An orchestrator can spawn threads and route plain-language requests directly into a Claude Code session. A pivotal feature for autonomous workflow sustainability is the resumeSessionId parameter. This allows a spawned sub-agent to detach, perform an investigation or compilation task, and later resume the parent conversation with its full historical context preserved. This capability prevents context amnesia during multi-step debugging flows, allowing the swarm to hand off tasks between Copilot and Claude Code seamlessly.
Structuring the Internal SWE Team: Roles and Continuous Improvement
With the orchestration and connectivity layers established, the internal team of developers must be distinctly structured. The architecture requires a fully autonomous team that runs parallel to the core system, capable of continuous scanning, ideation, and implementation.
The Creative Optimization Agent
A defining feature of this advanced swarm is the inclusion of a proactive, creative optimization agent. Traditional automation is purely reactive; it waits for a trigger or an error. The creative agent operates on a continuous loop, analyzing current practices, codebase telemetry, and deployment metrics. It autonomously asks: "How can we improve this specific area? How can we optimize the workflow?"
When this agent identifies a potential optimization—such as a redundant database query pattern or an inefficient CI/CD pipeline step—it formulates a hypothesis. It sends specific A2A requests to the investigation agents to collect data on the current implementation. The investigation agents utilize Deep Research capabilities to scan external open-source repositories for best practices and consult the internal Deep Wiki to understand the historical context of the existing code. The creative agent then synthesizes this data into a robust proposal through several iterations, preparing it for peer review.
The Council Deliberation Pattern
Before any major architectural change or creative optimization is implemented, it must pass through a "Council" deliberation phase. Utilizing the BeeAI framework's RequirementAgent, the system orchestrates a multi-agent debate. The Council consists of agents assigned specific personas: a Business Logic Agent (evaluating the impact on user experience and cost), a Technical Architect Agent (evaluating performance and scalability), and a Security Agent (evaluating vulnerabilities).
These agents discuss the creative proposal, challenging its assumptions and refining its parameters. This rigorous, multi-perspective refinement acts as a powerful safeguard against individual model hallucinations or short-sighted optimizations. Once the Council reaches a consensus and the proposal is thoroughly refined from both a business logic and technical perspective, the finalized specification is sent to Claude Code (acting via acpx) for a final, high-level code review and approval before entering the development pipeline.
Operationalizing the Swarm: A Comprehensive Production Use Case
To fully illustrate the autonomy, self-healing capacity, and A2A-driven coordination of this architecture, it is necessary to trace the lifecycle of a complex failure from initial detection through to autonomous rollback evaluation.
Phase 1: Detection and Triage
Scenario: A specialized Job Scraping agent, responsible for aggregating external data, runs into an operational issue. After successfully scraping 20 jobs, the target website implements a dynamic anti-bot measure, presenting a reCAPTCHA challenge that the scraper cannot bypass. The scraping agent fails repeatedly, throwing network timeout errors and DOM parsing exceptions.
1. Monitoring and Alert Generation: A dedicated Monitoring agent operates continuously, analyzing the telemetry and stdout streams of all active services. Awakened by the statistical deviation in the error logs and the warning signals emitted by the scraping module, the Monitoring agent assesses the severity. Recognizing a constant failure pattern that breaks a critical data pipeline, it immediately opens an urgent ticket in the enterprise ticketing system (e.g., Jira) and logs a mirrored issue on the project's GitHub repository.
2. Immediate Triage: Within seconds of the ticket creation, a Triage agent intercepts the webhook. Using semantic analysis, the Triage agent reviews the error stack trace. It categorizes the issue as an external interface failure requiring specialized web automation debugging. Utilizing A2A discovery, it identifies the Investigation Team and assigns the ticket to them, passing along the precise log snippets and the context of the failure.
Phase 2: Deep Investigation and the Think Tank
3. Specialized Sub-Agent Instantiation: The Investigation Team is awoken by the A2A payload. The team's orchestrator analyzes the triage report and determines that two specialized sub-agents are required: a Database Diagnosis Agent to verify data integrity up to the point of failure, and a Browser Automation Agent to reproduce the reCAPTCHA block.
4. Data Collection and Deep Research: These sub-agents operate in parallel. The Browser Automation Agent utilizes an MCP server to spin up a headless browser, attempting to replicate the scraping run to capture the exact DOM state and network headers when the reCAPTCHA triggers. Simultaneously, the Database Diagnosis Agent consults the Deep Wiki—powered by Project NANDA—to review the architectural history of the scraping module and understand its retry logic. Furthermore, the agents execute Deep Research workflows, querying external open-source repositories to discover known bypass strategies or alternative API endpoints for the target site.
5. Synthesis and Technical Reporting: The investigation sub-agents return their findings to the primary Investigation orchestrator. The team engages in a "think tank" process, cross-referencing the DOM analysis with the Deep Research findings. They refine the data, deciding precisely which code snippets, log files, and architectural examples are relevant to share. They author a comprehensive technical report detailing the reCAPTCHA implementation and proposing a transition to a proxy-rotated, headless API extraction method. This report is published directly to the GitHub issue.
6. Inter-Team Signaling: With the diagnostic phase complete, the Investigation Team sends a structured A2A signal to the Development Team. This signal confirms the completion of the investigation stage, transferring ownership of the ticket alongside the synthesized technical report, thereby preventing the Development Team from wasting tokens on redundant data gathering.
Phase 3: Development and The Ralph Wiggum Loop
7. Strategic Sub-Agent Allocation: The Development Team receives the A2A handoff. The orchestrator reviews the technical report and formulates a development strategy. Recognizing the complexity of integrating proxy rotation and API extraction, the orchestrator decides that three sub-agents are required. To adhere to the strict acceptance criteria regarding token efficiency, it employs dynamic model routing. It allocates two Claude 3.5 Sonnet agents to actively rewrite the scraping logic in two distinct codebase areas, and one faster, cheaper Claude 3 Haiku agent tasked with inline documenting and generating intermediary unit tests.
8. Introducing the Ralph Wiggum Loop: To ensure the development agents focus strictly on solving the reCAPTCHA bug before attempting to build additional logic on top of failing code, the architecture enforces the "Ralph Wiggum Loop". Originally conceptualized as a persistent bash loop, this methodology requires the LLM to repeatedly attempt a fix, execute the code, and face the raw, unfiltered output of its failures.
The loop prevents "context rot" by externalizing state. Progress does not persist in an endlessly expanding LLM context window; it lives in the local files and Git history. During each iteration:
* The Sonnet agents find the highest-priority incomplete task in the .agent/tasks.json file.
* They implement the proxy logic and run the tests generated by the Haiku agent.
* If the code fails (e.g., a proxy connection timeout), the loop feeds the exact stack trace back to the agents in a fresh context window, picking up precisely where the last iteration left off. This deterministic looping continues relentlessly until the Sonnet agents produce a stable, secure patch that passes all local unit tests. The Development Team then signals the E2E Testing Team.
Phase 4: Sandboxed Validation and Iteration
9. Parallel E2E Testing: The E2E Testing Team receives the proposed patch and initiates a rigorous validation sequence within an OpenHands-managed, parallel sandboxed environment. The orchestrator duplicates the environment to run simultaneous test vectors. First, the team executes the scraper against mock data to verify internal logic. Next, they inject real data into the sandbox to test the proxy rotation mechanism against actual network conditions. Finally, they run the scraper using designated test accounts (strictly insulated from the production database) to ensure the reCAPTCHA is successfully bypassed.
10. The Wider Iterative Loop: During the real-data sandbox test, a timeout edge case is discovered. The Testing Team compiles an error report and sends it back to the Investigation Team via A2A (returning to Step 6). The Investigation Team briefly analyzes the new timeout, updates the technical report, and hands it back to the Development Team (Step 7). The Ralph Wiggum loop re-engages to patch the timeout. This wider macro-loop continues across the team boundaries until the fix achieves a 100% pass rate, successfully handling all defined edge cases.
Phase 5: Deployment, Governance, and Autonomous Rollback
11. Injection and Active Monitoring: With testing complete, the Deployment Team assumes control. Operating under strict CI/CD governance, the deployment agents smoothly inject the change into the core automation system via GitOps protocols. The injection is performed in parallel, utilizing a canary release strategy. Simultaneously, the Deployment Team spins up the Monitoring Team, instructing them to specifically watch the network latency metrics and error rates associated with the newly deployed proxy logic.
12. Autonomous Rollback Evaluation: In a traditional CI/CD pipeline, an anomaly triggers a pager alert, requiring human intervention. In a full autonomy architecture, the system relies on active investigation. If the Monitoring Team detects that the new proxy logic is causing severe memory leaks—a problem arguably worse than the initial reCAPTCHA block—the Evaluation Orchestrator intervenes. It autonomously decides that the new deployment is detrimental. It immediately triggers a targeted autonomous rollback, utilizing OpenHands' state preservation capabilities to revert the Git commit and restore the previous stable container image. The system maintains stability while placing the ticket back into the development queue.
Assuming the deployment is successful and metrics remain stable, the process moves to finalization.
Phase 6: Documentation and Closure
13. Knowledge Integration: A functional fix is incomplete without proper documentation. The Documentation Team is activated to ensure the system's long-term maintainability. These agents parse the newly merged code, update the internal architectural documents, refresh the Deep Wiki entries, and ensure all Git tracking is perfectly up-to-date. By guaranteeing that the documentation matches the actual codebase behavior, the swarm prevents future agents from hallucinating based on outdated specifications. The urgent ticket is automatically closed, the teams spin down, and the swarm returns to its baseline monitoring state.
Deterministic Transformation and Token Economics
A critical acceptance criterion for this architecture is extreme operational efficiency. Running massive multi-agent swarms continuously can result in astronomical API costs and token waste if not rigorously governed. The system must rely on free tiers or open-source tools for minor tasks, reserving expensive frontier models (such as Claude 4.6 Opus) strictly for major overall planning, complex architectural design, and the final stages of the Council deliberation.
Dynamic Model Routing
To achieve this, the orchestrator employs intelligent, dynamic LLM routing via high-performance gateways. When a task is generated, the routing layer analyzes its complexity. Simple syntactical linting, log formatting, or basic data retrieval tasks are automatically routed to local open-source models (e.g., Llama 3) or highly efficient, lower-cost models (e.g., Claude Haiku). Only when the task requires profound logical reasoning, multi-step deduction, or cross-system architectural planning does the router escalate the request to the expensive Opus 4.6 model. This cascading routing approach reduces inference costs by up to 85% while maintaining parity with top-tier model performance.
Transforming Traces into Deterministic Automations
The most profound optimization mechanism within the swarm is its ability to transform initial, exploratory agentic runs into deterministic, vector-based automations over time.
When the swarm encounters a novel issue, it relies heavily on probabilistic LLM reasoning to navigate the problem space. However, if the exact same issue occurs repeatedly, utilizing an LLM to solve it each time is an unjustifiable waste of compute. To solve this, the architecture employs a combination of Semantic Caching and Trajectory Distillation.
Semantic Caching: As agents execute tasks, their queries and successful responses are stored in an enterprise vector database (such as Qdrant or Redis). When a new query is generated, the system calculates its semantic vector embedding. If the embedding closely matches a previously solved problem (based on a high confidence threshold), the system bypasses the LLM entirely and returns the cached trajectory. This reduces response times from several seconds to sub-10 milliseconds and effectively drops the LLM API cost for that task to zero.
Trajectory Distillation: Beyond simple caching, the system analyzes successful execution traces—the step-by-step Thought, Action, and Observation sequences generated during the Ralph Wiggum Loop. Through behavioral cloning, the orchestrator identifies highly repeatable patterns. If an agent consistently resolves a specific database desynchronization by executing the exact same series of bash scripts and SQL commands, the orchestrator can compile this sequence into a deterministic automation (e.g., a standard GitHub Action or an n8n workflow).
The next time the Monitoring agent detects this specific desynchronization, it triggers the deterministic script directly, completely bypassing the cognitive agentic layer. This mechanism ensures that the swarm is constantly pushing solved problems down into the deterministic layer, freeing up the expensive LLM cycles to focus solely on novel, unprecedented challenges.
Governance, GitOps, and Blast Radius Containment
Operating an autonomous SWE team with write access to production environments introduces severe security and stability risks. A hallucinating agent could inadvertently expose API credentials, delete critical infrastructure, or merge malicious code. Therefore, strict development and CI/CD governance must be enforced through defense-in-depth architectures.
Sandboxing and Explicit Boundaries
Frameworks like OpenHands provide the necessary infrastructure for blast radius containment. Every agent operates within an ephemeral, Docker-containerized execution environment. These sandboxes are strictly isolated from the host system. API keys and credentials are only loaded dynamically via environment variables and are aggressively stripped from any configuration files before the agent interacts with them, preventing accidental commits to version control.
Furthermore, tool access is granted on a principle of least privilege. While a deployment agent may have access to production credentials, an investigation agent is strictly limited to read-only tools and read-only database replicas. The fs.workspaceOnly: true parameter ensures that agents cannot traverse directories outside their explicitly assigned project scope.
Agentic Governance and Human-in-the-Loop Escalation
To sustain good GitOps practices, the system incorporates agentic governance. Specific tools that pose a high risk—such as executing arbitrary bash commands on staging servers (exec) or modifying fundamental CI/CD YAML files—can be flagged within the orchestration framework to require explicit human approval. The framework emits a pending approval request to a UI or Slack channel, pausing the agent's execution until a human engineer validates the command.
Additionally, systems like FeatBit provide active investigation and skills-based access to observability stacks. If a deployment goes awry, the system relies on policy-based, deterministic rollbacks rather than panic-driven reactions. The intelligence layer audits the deployment, checks the integrity floor, and utilizes autonomous rollback protocols to restore the prior state, logging an explicit traceability log to ensure the failure mode is incorporated into the swarm's future training data.
